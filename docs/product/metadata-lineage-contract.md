# 元数据血缘合同

当前血缘为有操作者与证据的人工确认关系。人工请求仅接受 `source_object_id`、`target_object_id`、`evidence`、`origin`，且 `origin` 必须是 `manual`。将文本标成 SQL 或采集器来源不会形成可信证明，真实 SQL 解析产边需要后续专用解析器和来源运行记录。

服务保存操作人的真实账号 ID、证据记录时间和两个端点的真实元数据版本。客户端不能填写或覆盖这些证据字段。编辑关系会重新确认端点和版本、记录本次操作人，资源版本及安全资源审计保留实际改动过程。

端点必须是同租户中已采集并处于 published 的真实元数据对象。仓储在写事务中对照内部 `metadata_catalog`、完整字段快照、结构指纹、实际资源属性和版本；SQLite 在 IMMEDIATE 事务内检查，PostgreSQL 沿租户图锁检查。真实外键保护被引用对象。自引用、重复上游/下游边及会形成依赖环的关系不能提交，检查和写边在同一事务，避免并发反向边都通过。

分析从同一数据库快照读取边和当前元数据摘要，PostgreSQL 使用 repeatable read。仅 draft/published 人工关系进入分析；inactive 关系不参与当前依赖。端点版本改变或证明失效后，保存的边标记 stale，当前路径不使用旧证据。旧版本未提供可信操作者/来源的关系返回 `invalid_edges`，不会自动升级为 SQL 血缘。

分析输入为 `root_object_id`（可选，默认当前关系的下游）、`direction`（upstream/downstream/both）、`max_depth`（1..20）、`max_nodes`（1..500）及 `max_edges`（1..1000）。数据库扫描最多 2000 条实际关系，累计人工证据最多 8 MiB。结果包含真实 `nodes`、`edges`、首次到达各对象的路径及深度、visited 数量、stale/invalid 边、环标志和明确截断原因。路径为实际可达对象的首次遍历路径，不声称已枚举全部可能路径；深度、节点、边或扫描容量达到边界时不能解释成完整影响分析。

孤立起点也必须由当前内部目录证明，缺失对象不会被生成占位节点。分析不执行 SQL，不修改底层物理数据，也不根据名称推断关系。

资产地图的兼容方向是 `asset_ids` 引用真实 `asset_entry`，资产的 `object_kind/object_id` 指向实际元数据、模型、指标等来源。元数据来源可投影上述真实血缘；跨类型资产关系需明确来自实际资源引用，并标注关系种类，不能将 UI 布局连线当作业务血缘。此合同尚不表示资产目录注册/发布及地图投影已经完成。
